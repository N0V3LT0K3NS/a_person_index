# Editorial Style Guide

This registry is not a marketing site and not a fandom wiki. The writing standard should be clear, sober, comparative, and explicit about epistemic boundaries.

## Core voice

- Prefer precise descriptive language over hype.
- State what the system is before stating whether it is useful.
- Keep source claims, ontology labels, and house inferences clearly separated.
- Treat weak-evidence but culturally important systems seriously without pretending they are stronger than they are.

## Notes template

Each `notes.md` file should use this section order:

1. `# {Canonical Name}`
2. `## What it is`
3. `## Why it matters`
4. `## What it is good for`
5. `## What it is weaker at`
6. `## Common misuse`

Notes should stay concise and legible. The goal is high-signal orientation, not exhaustive narrative.

## Resource notes

- `resources.yaml` notes should say why the source matters.
- Prefer phrases like `Official overview`, `Technical report`, `Seminal paper`, or `Secondary reference`.
- Avoid filler such as `useful resource` or `helpful page`.

## Crosswalk rationale

- Name the actual overlap, not just that the systems are `related`.
- Say whether the mapping is strong, loose, partial, inverse, historical, or incommensurable.
- Avoid one-to-one language unless the constructs are unusually close.

## Inference standard

- Inferences should read like house analysis, not like source marketing copy.
- Prefer one strong sentence over several vague ones.
- When confidence is medium or low, the wording should reflect that uncertainty.

## Presentation standard

- Generated docs should expose constructs, resources, crosswalks, risks, and use cases in a consistent order.
- Count labels and section labels should read naturally.
- If a new docs surface is added, keep it aligned with the existing muted/neutral visual language rather than introducing a new visual system.
