# Comparison Shapes

Contextual and pairwise work becomes weak quickly when the comparison itself is
left implicit.

Comparison shapes are the layer that makes the comparison scaffold explicit
before a host chooses an artifact or starts rendering.

## What a comparison shape is

A comparison shape names the input contract for a specific kind of comparison.

It answers questions like:

- Is this one person across time?
- Is this one person across roles or contexts?
- Is this two people side by side?
- Is this two people inside a declared relational question?

## Why this layer exists

Run modes are broad.

Protocols start after the comparison shape is already assumed.

Comparison shapes sit between those layers and keep the host from inventing the
setup ad hoc.

## What they declare

A comparison shape can make explicit:

- the scope of the comparison
- the declarations the user or host must provide
- the declaration fields that can be checked before execution
- the artifact classes that usually fit
- the protocols that usually fit
- the cautions that matter before execution begins

## Comparison preflight

Once a comparison shape is chosen, use comparison preflight to check whether the
necessary declarations have actually been provided.

That is the layer that keeps contextual and pairwise work from moving into
artifact or workflow selection while the scaffold is still underspecified.

## Recommended order

For contextual or pairwise work, the clean order is:

1. identify the run mode
2. identify the comparison shape
3. run comparison preflight with explicit declarations
4. inspect capabilities
5. choose the artifact, expression, workflow recipe, and actualization path
6. execute

## Boundary rule

Comparison shapes do not create compatibility truth, relationship truth, or
developmental truth by themselves.

They only make the comparison scaffold explicit so later work can stay honest.
